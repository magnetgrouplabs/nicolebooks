## Chip precedence table (first match wins)

| # | Condition | Label | Variant |
|---|-----------|-------|---------|
| 1 | `file.status === 'duplicate-excluded'` and `file.postedAt` present | `Already entered on {postedAt}` | destructive |
| 2 | `file.status === 'duplicate-excluded'` | `Already entered` | destructive |
| 3 | `file.status === 'duplicate-in-batch'` | `Duplicate in this scan` | secondary |
| 4 | `file.status === 'not-ready-skipped'` | `Not downloaded yet, re-scan shortly` | outline |
| 5 | `file.status === 'unsupported-skipped'` | `Unsupported` | outline |
| 6 | `parse?.status === 'parse-failed'` | `Could not read` | destructive |
| 7 | `isFlagged(parse)` is true | `Needs review` | destructive |
| 8 | `parse?.status === 'cached'` | `Already read` | secondary |
| 9 | `parse?.status === 'parsed'` | `Ready to review` | default |
| 10 | `parse` is undefined (loaded, not read yet) | `Loaded` | secondary |

**Why rows 1-5 sit above the parse rows.** A file with a non-loaded status never entered the parse
pipeline (BillsScreen only sends `status === 'loaded'` files to `parse.parseBatch`), so its file
status is the only fact that exists about it. Putting it first also means that if a future change
ever parses an included-anyway duplicate, the dedupe warning cannot be overwritten by a cheerful
"Ready to review". Losing a duplicate warning is the worse failure, and it is safe to order this
way ONLY because WR-10 is enforced in the field list, not by the chip (see below).

**Why "Could not read" and "Needs review" beat "Loaded".** "Loaded" carries no information once a
parse result exists; it is precisely the bland state the user complained about. A parse failure and
a failed deterministic check are the two states that require the user to act.

**Why "Needs review" beats "Cached".** The cache hit is a cost/provenance fact, not something the
user acts on, and it is already reported in the batch summary line ("N already read"). A flagged
bill wearing a calm "Cached" chip is the chip-level version of the exact WR-10 failure.

**Color semantics this produces.** default/purple = done and good; secondary/grey = in progress or
benign no-op; destructive/red = needs you; outline = skipped, not in the batch. "Loaded" moves from
default to secondary as a direct consequence of making the color mean something. That is inherent
to the requested change, not a restyle.

**Deliberately NOT added:** a "Reading..." in-flight chip. `ScanRow` has no access to the batch
parsing state and the screen already shows "Reading bills: parsing N of M" above the list. Adding a
prop for it is scope the user did not ask for.

## "In batch": deleted, not merged

Inclusion is a different axis from pipeline status, so it cannot be folded into the chip without
inventing a compound label like "Already entered, included anyway". But it does not need its own
badge either: the toggle button sitting immediately next to it already reads **"Remove from batch"**
when the file is included and **"Include anyway"** when it is not. "Remove from batch" can only ever
render for a file that is in the batch, so the badge is pure redundancy two elements away from the
control that states the same thing unambiguously and is also actionable.

So: delete the `{included && <Badge>In batch</Badge>}` element. Keep the `included` prop (BillsScreen
passes it) and keep it driving the button label. Keep both buttons exactly as they are. Aggregate
inclusion is still reported by the existing "N files in batch" line above the list.

## Null field handling: omit, unless flagged

Omit a null field, EXCEPT when that field carries a flag, in which case render it with the explicit
value text `Not found` plus its marker.

This mirrors what the main process already decided. `computeConfidence` omits ungradeable nulls
("so Phase 6 does not badge an empty cell") but deliberately keeps a flagged field in the map "even
when its value is null, because the flag itself is the thing to show". A cash receipt with no tax
line legitimately has `taxCents: null` and rendering "Tax: not found" on every such row is the blank
noise the task warns against; but `money:taxCents` fires only when the document HAD a tax value and
it was unreadable, and hiding that row would hide a failed check.

`vendor` and `totalCents` are the two required fields and are ALWAYS rendered, flagged or not. An
empty-string vendor renders as `Not found`.

## Confidence levels surfaced: `flagged` only

Do not surface `low`. On the image-only route there is no embedded text to ground against, so
confidence.ts lands EVERY non-flagged field at 'low' by design. Marking 'low' would paint a marker
on every field of every phone-photo receipt, which is noise, not signal. `flagged` is the only level
that means "a deterministic check failed on THIS field". The rich per-field confidence UI is Phase 6
(D-18) and this is deliberately not that.
</design_decisions>
